### 1. 通用约定

#### 1.1 基础信息
- **基础 URL**：`http://127.0.0.1:8080`（开发环境）
- **数据格式**：`application/json`
- **字符编码**：`UTF-8`

#### 1.2 认证方式与 Token 策略
需要认证的接口必须在请求头中携带 Bearer Token：
```
Authorization: Bearer <token>
```
Token 通过登录接口获取。

**Token 有效期约定：**
- **有效期**：Token 自颁发起 **7 天（168小时）** 后失效。
- **刷新机制**：当前版本采用单 Token 机制。客户端应在 Token 过期前引导用户重新登录，或由服务端在后续版本中引入 Refresh Token 机制以提供更流畅的体验。

#### 1.3 响应状态码语义
| 状态码 | 含义 |
|--------|------|
| 200 | 请求成功 |
| 201 | 资源创建成功 |
| 400 | 请求参数错误 |
| 401 | 未认证或 Token 无效/过期 |
| 403 | 权限不足 |
| 404 | 资源不存在 |
| 409 | 资源冲突（如用户名已存在） |
| 500 | 服务器内部错误 |

#### 1.4 错误响应格式
当发生 4xx/5xx 错误时，响应体统一采用以下 JSON 格式。`error` 字段内容必须使用需求文档中定义的精确中文提示，以保证前后端错误处理的一致性并提高开发准确性：
```json
{
  "error": "针对该错误的中文描述信息"
}
```
**常见错误信息对照表示例：**
| 状态码 | 场景 | `error` 字段内容 |
|--------|------|------------------|
| 400 | 库存为空时智能推荐 | `您的库存为空，请先添加食材` |
| 400 | 图片上传格式不符 | `请选择 JPG 或 PNG 格式的图片` |
| 400 | 图片上传大小超限 | `图片大小不能超过5MB` |
| 400 | 密码强度不足 | `密码需包含字母和数字，至少6位` |
| 400 | 修改密码原密码错误 | `原密码不正确` |
| 400 | 找回密码用户名邮箱不匹配 | `用户名或邮箱不正确` |
| 400 | 评分超出范围 | `评分必须在1到5之间` |
| 403 | 编辑他人菜谱 | `仅可编辑自己投稿的菜谱` |
| 403 | 修改他人评论 | `无权限操作他人的评论` |
| 403 | 管理员自毁角色 | `不能修改自己的角色` |
| 403 | 删除最后一名超管 | `系统必须保留至少一名超级管理员` |
| 404 | 资源不存在 | `请求的资源不存在` |

#### 1.5 分页约定（强制统一）
对于所有列表类接口，**必须**使用以下查询参数：
- `page`：页码，从 1 开始，默认 1
- `size`：每页数量，默认 20，最大 100

**所有列表接口的响应体格式必须严格遵守以下结构：**
```json
{
  "data": [ /* 数据数组 */ ],
  "pagination": {
    "page": 1,
    "size": 20,
    "total": 100,
    "total_pages": 5
  }
}
```

**默认排序规则：**
除非接口单独说明，所有列表类接口的默认排序均为按创建时间倒序（`created_at DESC`）。

### 2. 用户认证相关（公开）

#### 2.1 用户注册（两段式）【v2.17 两段化】
- **方法**：`POST`
- **路径**：`/api/register`
- **请求体**：
```json
{
  "username": "testuser",
  "password": "123456",
  "email": "test@example.com"
}
```
- **字段说明**：`username` 为登录凭证（唯一标识），`email` 为必填项，用于密码找回等安全操作。
- **成功响应**（响应保持统一，不透露邮箱是否已注册）：
  - 状态码：`200 OK`
  - 响应体：
```json
{
  "message": "我们已向该邮箱发送邮件，请按邮件提示继续。"
}
```
- **说明**：两段式注册第一步——服务端校验用户名 / 密码 / 邮箱格式后**不直接建号**：
  - 邮箱未注册 → 写入待验证记录（15 分钟）并向该邮箱发送 **6 位数字验证码**邮件；
  - 邮箱已注册 → 不建号、不写记录，向该邮箱发送「您已有账户，请登录或重置密码」提示邮件（防枚举：页面层不暴露注册状态，差异只体现在邮件内容）。
  - 开发模式（未配置 SMTP）：邮件内容打印到服务端日志，接口响应保持统一。
- **失败响应**：
  - `400`：用户名、密码或邮箱为空，或邮箱格式无效
  - `409`：用户名已存在

##### 2.1.1 完成注册（验证码核验）【v2.17 新增】
- **方法**：`POST`
- **路径**：`/api/register/verify`
- **请求体**：
```json
{
  "email": "test@example.com",
  "token": "123456"
}
```
- **成功响应**：`200 OK`
```json
{
  "message": "注册成功"
}
```
- **失败响应**：
  - `400`：邮箱格式无效 / 缺少验证码 / 验证码无效或已过期
  - `409`：用户名已被占用（请更换后重新注册）或邮箱已被注册（请直接登录）
- **说明**：核验通过后在同一事务中创建用户并删除待验证记录。

#### 4.1 获取公开菜谱列表（分页）【v2.2 增强列表字段】【v2.4 增加排序与评分筛选】【v2.7 增加口味、烹饪技法、热量、食材类型筛选】
- **方法**：`GET`
- **路径**：`/api/recipes/public`
- **查询参数**：
  - `?page=1&size=20` (分页)
  - `cuisine`: 菜系，如 "中式"、"西式"
  - `meal_type`: 菜品类型，如 "主食"、"汤"
  - `flavor`: 口味，如 “清淡”、“麻辣”
  - `cooking_method`: 烹饪技法，如 “炒”、“炖”、“蒸”
  - `ingredient_type`: 食材类型，如 “荤”、“素”

  - `sort_by`: 排序方式，可选值：`popular`（按浏览量降序，对应需求中的"热度排序"）、`rating`（按平均评分降序）、`newest`（按发布时间降序）。默认 `newest`。
  - `min_rating`: 最低平均评分（0.0 - 5.0），仅返回平均评分不低于该值的菜谱。
- **认证**：不需要
- **成功响应**：**统一分页格式**，列表项包含浏览量和平均评分，以及 `cooking_method`、`flavor` 等分类字段。
```json
{
  "data": [
    {
      "id": 1,
      "name": "番茄炒蛋",
      "description": "经典家常菜",
      "image_url": "https://...",
      "cooking_method": "炒",
      "flavor": "清淡",

      "view_count": 256,

      "author_name": "testuser"
    }
  ],
  "pagination": { ... }
}
```
- **字段说明**：
  - `view_count`：该菜谱累计被查看的次数。
  - `avg_rating`：该菜谱的平均评分（保留一位小数），若无人评分则为 `0.0`。
  - `cooking_method`：烹饪技法。
  - `flavor`：口味。
  - `ingredient_type`：食材类型（荤/素等）。
  - `calories`：菜谱总热量。

#### 4.2 智能推荐菜谱（需认证）【v1.5 增强】【v2.3 字段统一】【v2.4 职责明确】【v2.5 边界强化】【v2.6 健康过滤标志】【v2.8 强化推荐策略描述】
- **方法**：`GET`
- **路径**：`/api/recipes/recommend`
- **说明**：本接口同时承担两项核心需求：
  1. **智能推荐**：根据用户偏好与库存自动推荐，综合匹配度评分（`match_score`）。
  2. **库存智能搜索**：当用户从库存界面触发“一键搜索”时，本接口同样提供基于库存食材与偏好的可用菜谱列表。客户端可通过上下文（如来源页面）区分推荐与搜索场景。
  缺失食材提供建议用量与单位，可直接用于批量添加购物车，客户端无需再做字段映射。
  库存为空时的错误处理：当用户库存中无任何食材时，服务端必须返回 `400` 错误，并携带描述信息 `"您的库存为空，请先添加食材"`，以对齐需求文档中提示用户的业务逻辑。

  **【v2.8 推荐策略说明】**
  服务端在计算推荐结果时，必须综合以下三层逻辑：
  1. **库存匹配度**：根据用户当前库存食材与菜谱所需食材的重合度计算基础匹配分。
  2. **健康忌口过滤（v2.10 两档化）**：服务端读取用户健康档案条件，按内置名单执行两级过滤（名单全量口径见 v2.11）：
     - **硬档（一票否决）**：菜谱食材命中下列名单即整道排除，强制执行、不可跳过——高血压：咸菜/腊肉/咸鱼/腐乳/榨菜；糖尿病：甜面酱/炼乳/果酱；高血脂：肥肉/猪油/黄油/奶油/五花肉/油炸/猪板油；痛风：海鲜/动物内脏/啤酒/浓汤/香菇/虾/蟹；
     - **软档（提示 + 降权）**：命中下列调味料时**不排除**，在推荐项上附提示文案（`health_notice`）并对匹配分轻微降权——高血压：盐/酱油/豆瓣酱；糖尿病：糖/白糖/冰糖/蜂蜜；
     - **软档补充（v2.12 钠阈值按量分级）**：高血压用户所遇菜谱整道钠含量 ≥800mg 且未命中上述软档调味料时，同样附钠提示文案并轻微降权（有软档命中时提示已覆盖"少盐"语义，不重复）；其余条件不触发钠提示。名单以服务端内置表（HealthConditionLists）为唯一事实源，本段落为契约快照；
     - 胃炎条件**不参与食材级过滤**（辛辣/生冷属饮食行为，无法映射为食材黑名单），仅由健康档案接口返回建议文案，服务端不据此剔除菜谱。
  3. **偏好加权**：根据用户设置的饮食偏好（`GET /api/users/me/preferences` 中的 `likes`、`dislikes`、`health_goal`），对候选菜谱进行加权排序。符合偏好的菜谱获得额外加分。

- **成功响应**：
```json

      "avg_rating": 4.5,
      "match_status": {
        "available_ingredients": [
          { "name": "鸡蛋", "quantity": 2, "unit": "个" },
          { "name": "番茄", "quantity": 1, "unit": "个" }
        ],
        "missing_ingredients": [
          { "name": "葱花", "quantity": 1, "unit": "把" }

      }
    }
```

- **失败响应**：
  - `400`：用户库存为空 (`{"error": "您的库存为空，请先添加食材"}`)
- **字段说明**：
  - `health_filter_applied`：布尔值。用户健康档案存在且本次查询因**硬档忌口**（名单见上方策略说明第 2 条）实际排除了至少一道菜谱时为 `true`；仅软档提示命中不置位。无健康档案或未命中硬档时为 `false`。

#### 4.14 烹饪模式实现说明【v2.2 增强声明】【v2.8 明确语音播报职责】
> **【设计声明】**
> 需求中定义的沉浸式烹饪模式（包括分步步骤引导、语音播报、计时器界面与提醒、烹饪进度保存/恢复）**完全是客户端本地功能**。服务端仅通过菜谱详情接口（4.4）提供 `steps` 数组（含每步 `duration` 字段）作为数据基础。

>
> **【v2.8 语音播报职责明确】**
> 语音播报功能由客户端调用**本地系统TTS（文本转语音）引擎**实现，服务端不提供任何语音合成或语音识别API。客户端应自行检测本地TTS引擎可用性：当本地引擎不可用时，客户端应自行处理降级提示（如显示“语音服务暂不可用”），并确保用户仍可通过手动操作继续烹饪流程。

  - `per_serving`：营养素含量（服务端自动计算 = 各食材按用量累加）。**当前版本语义：整道菜营养合计，非单份**；客户端以"营养合计"文案呈现（后续可引入份数 `servings` 除法升级为真正的每份值）。
  - `ingredients_breakdown`：各食材对总营养的贡献明细（未收录/无法换算的食材不计入）。
  - `excluded_ingredients`：未计入营养的食材列表（`name` 为投稿时原始食材名，`reason` 取值 `未收录`/`无法换算`）；全部计入时为空数组。客户端应提示用户合计未包含这些食材，避免把残缺合计当作完整数据。
  - `health_notes`：基于当前菜谱营养特征按阈值规则生成的健康提示（无命中则为空串）。
  - `has_data`：是否有可用营养数据；`false` 表示该菜谱暂无营养报告（如食材全部未收录），客户端应展示空态而非 0 值。**兼容说明**：升级前创建的旧格式菜谱（只有 flat 四项、无 `per_serving`）服务端会回退合成 `per_serving`（纤维/钠/维C 为 0）并返回 `has_data:true`，与详情页判定一致。
- **失败响应**：
  - `404`：菜谱不存在

### 7. 管理接口（需管理员权限）

**权限说明（v2.1 明确）（v2.3 补充角色枚举）（v2.5 强化角色保护规则）：**
GoCook 系统管理员分为两级：
- **内容管理员（Moderator）**：可访问菜谱审核、公告与通知管理、查看数据统计、查询用户行为日志等日常运营接口，但**不能**访问用户账户与权限管理（7.1）以及角色变更相关操作。
- **超级管理员（Super Admin）**：可访问所有管理接口，包含用户账户管理、角色管理、系统维护等。
所有需要管理员权限的接口均需验证用户角色。用户角色枚举值定义如下：`user`（普通用户）、`moderator`（内容管理员）、`super_admin`（超级管理员）。未授权返回 `403`。

**超级管理员自保护规则（强制）**：
1. **禁止自毁**：任何超级管理员都**绝对不能**通过 API 修改自己的 `role` 或 `status` 字段，也不能删除自己的账户。服务端必须校验操作者 `user_id` 与目标 `user_id`，若相同则返回 `403`。
2. **最后一人保护**：系统必须始终保留至少一名 `super_admin`。若操作（降级或删除）会导致超级管理员数量为零，服务端必须拒绝该操作并返回 `403`，提示“系统必须保留至少一名超级管理员”。
3. **角色变更日志**：所有角色变更操作（包括尝试但被拒绝的操作），均需记录到永久操作日志中。

  - `403`：尝试修改自己的角色 (`{"error": "不能修改自己的角色"}`)；或尝试降级/删除最后一名超级管理员 (`{"error": "系统必须保留至少一名超级管理员"}`)

### 8. 运维与扩展功能边界说明

以下功能需求根据系统架构设计，**不通过 RESTful API 对外暴露**，而是由运维层面的工具或客户端本地能力实现。

| 功能点 | 实现策略 |
|--------|----------|
| **菜谱分享** | 客户端生成分享链接，调用系统分享能力。服务端预留 `POST /api/recipes/:id/share` 端点以支持未来高级特性（如带时效的分享 Token）。 |
| **广告管理** | 此功能为后台管理范畴，但 V1.0 版本暂不提供 RESTful API。当前可暂以静态配置或运维方式实现。后续视运营需求，将独立设计广告管理端点（`/api/admin/ads`）并纳入后续版本。 |
| **日志监控** | 服务器本地脚本监控或使用 ELK 等日志系统。 |
| **数据备份** | 使用 PostgreSQL 自带工具（pg_dump）或 Cron 定时任务。 |
