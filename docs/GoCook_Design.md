1. **引用规约**：引用代码一律"文件 + 符号名"（如 `RecipeServiceImpl::getRecommendedRecipes`），**不写行号**——行号会漂移。
2. **编号规约**：领域规则编号 `R#`、决策编号 `D-NN`；编号一经分配不再变更。决策正文只在第 4 章单点维护，领域节以"（见 D-NN）"引用。
3. **更新触发**：语义 / 行为变更 → 同一 commit 更新本文档，并在附录 A 追加修订记录、更新头部"最后更新"。
4. **里程碑体检**：阶段性收尾时 grep 抽查已拆除功能的残留表述（如搜"离线写队列"确认无把已拆功能当现役的描述）。
5. **每节写作模板**：职责一句话 → 核心规则（表，R#）→ 唯一事实源（代码符号）→ 设计决策（引用 D-NN）→ 边界与坑。
6. **密度优先**：只写"跨文件才能还原"的信息；细节能用指针（文件 + 符号）说清的不展开，数值型细节以代码为唯一事实源、仅在定义行为时写入。
7. **目录与锚点**：标题前放显式锚点 `<a id="sX-Y"></a>`（跨渲染器可跳转，与学习资料的目录方案一致）；新增 / 改名章节时同步目录、检索指南与锚点。

## 1. 系统总览与架构约定

**一句话**：菜谱管理与智能烹饪推荐系统——Qt QML 桌面客户端 + C++（httplib）服务端 + PostgreSQL，C/S 架构。核心差异化是"从冰箱出发"：库存 / 偏好 / 健康条件驱动的推荐，以及"库存 → 推荐 → 购物清单 → 已购回流"闭环。

**调用链**：`QML 页面 → ViewModel → HttpGoCookApi →［HTTP］→ Router / 中间件 → Handler → Service → Repository → PostgreSQL`。

**模块地图**：

| 模块 | 职责 | 入口 |
|---|---|---|
| `client/qml` + `client/viewmodels` | UI 与状态（MVVM） | 5 个 ViewModel：Auth / Recipe / Inventory / ShoppingList / Notification |
| `client/api` | 网络层 | `HttpGoCookApi`（登录守卫、错误分层、重试） |
| `client/database` | 本地缓存 | `LocalDatabase`（SQLite 单例） |
| `contracts/` | 共享契约与数据模型 | `DataModels.h` / `IServices.h` / `IGoCookApi.h` / `I*Repository.h` |
| `server/` | 服务端全链 | `Router → Handler → Service → Pg*Repository` |
| `server/common` | 基础设施 | `DbExecutor` / `ErrorHelper` / `UploadPaths` / `UploadFileServer` / `ImageUploadRules` / `JsonSerializer` / `ConnectionPool` |

**设计约定**：契约先行（接口层独立，双端共享 DataModels）；依赖注入在 `server/main.cpp` 手工组装全依赖树（无框架）；分层依赖单向。

<a id="c2"></a>
## 2. 领域设计

> 各节按 0.4 模板展开：职责 → 核心规则（R#）→ 唯一事实源 → 设计决策 → 边界与坑。

<a id="s2-1"></a>
### 2.1 菜谱域：投稿 / 审核 / 版权查重

**职责**：菜谱全生命周期——浏览 / 搜索 / 投稿 / 编辑 / 删除；审核与后台管理当前为骨架状态（见 R5）。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 投稿状态机 | 投稿入库恒为 `pending`；`recipes.status` ∈ {pending, approved, rejected}；**编辑后恒回 `pending`**（重新审核） |
| R2 | 版权查重（自动） | `existsByContent`：食材 JSONB 整体相等 + 步骤（剔除 `image_url` 字段、按 order 排序后）相等 + 仅与 `approved` 菜谱比对 → 命中 409「食材与步骤与现有菜谱完全一致，疑似侵权」；服务端内部执行、不暴露 API 端点 |
| R3 | 编辑权限 | 仅作者本人（403「仅可编辑自己投稿的菜谱」）；**可编辑任意自己稿件（含已发布）**，编辑即回 `pending`（复核维持放开，见 [D-12](#d-12)）；编辑重算营养（见 2.5） |
| R4 | 删除权限 | 仅作者本人（403）；**已通过审核的菜谱不可删除**（403）；删除 = 两段式：读信息 + 提交 → 清理图片文件（失败仅 WARN 不阻塞）→ 第二个事务 DELETE |
| R5 | 审核为骨架 | 审核端点已注册，但 `AdminServiceImpl` 全为 501「功能暂未实现」：待审列表 / 通过 / 拒绝 / 批审 / 公告发布 / 定向通知均未实现；用户侧「我的投稿按状态筛选」已可用 |

**唯一事实源**：`PgRecipeRepository::existsByContent` / `update` / `deleteRecipe`；状态值 `create_all_tables.sql`；骨架状态 `AdminServiceImpl`。

**边界与坑**：

- 查重基准仅 `approved`：与待审 / 未通过稿件之间不查重；
- `deleteRecipe` 手写不包 `executeDb`（跨两个连接 + 文件系统，无法单事务，注释留档）；
- 编辑已发布菜谱 → 回待审状态；审核功能尚为骨架（见 R5）期间，该菜谱会暂时离开公开列表，重新发布依赖审核落地（已知状态）；
- 2026-09 收口：api-spec 1.4 旧错误行已随 spec v2.16 按现实修正。

<a id="s2-2"></a>
### 2.2 推荐引擎

**职责**：根据用户库存、饮食偏好与健康条件，对已发布菜谱做过滤与加权排序，输出带匹配明细与健康提示的推荐列表。同一端点同时承担"库存一键搜索"场景（客户端按来源页面区分语境）。

**三层结构**：库存匹配（SQL 算）→ 健康过滤（Service 两档）→ 偏好加权 + 多样化（Service）。

**流程（九步）**：库存非空校验 → 加载偏好 → 加载健康档案（构建硬档集合）→ 拉候选（size × 3）→ 两档过滤（硬档剔除 / 软档挂提示）→ 加权评分 → 排序 → 多样化裁切 → 响应组装。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 库存匹配口径 | `match_score` 初值 = 命中食材条目数 ÷ 菜谱食材条目总数（库存侧按小写名去重——同名多单位行不重复计数；明细展示取最近录入行。匹配只看"有没有"，不看数量） |
| R2 | 库存空即拒 | 库存总数为 0 → `400 您的库存为空，请先添加食材` |
| R3 | 候选放大 | 取 `size × 3` 条候选：过滤与多样化会砍掉一批，多取才能凑满目标条数 |
| R4 | 硬档一票否决 | 菜谱任一食材（无论是否在库存中）命中硬档名单 → 整道剔除，优先级高于一切评分 |
| R5 | 软档只提示 | 软档名单命中 → 不剔除；附 `health_notice` 并轻微降权 -0.03（单次，不按命中食材数量叠加） |
| R6 | 钠阈值分级 | 高血压用户 + 整道钠 ≥800mg + 未命中软档 → 附钠提示 + 同一 -0.03（与软档互斥不重复） |
| R7 | 五维加权 | `finalScore = 库存×0.50 + 偏好×0.25 + 流行×0.10 + 新鲜×0.05 + 营养×0.10`，钳位 [0,1]、保留两位 |
| R8 | 偏好调制 | 风味命中喜欢 +0.15 / 标签命中 +0.10 / 含厌恶食材 -0.50（可叠加；厌恶惩罚足以翻转排名） |
| R9 | 流行 / 新鲜 / 营养 | 平均评分 ≥4.5 → +0.08、≥4.0 → +0.05；7 天内投稿 +0.05；健康目标命中 +0.10（高蛋白 / 低卡 / 减脂 / 增肌，阈值见常量区） |
| R10 | 多样化裁切 | 同口味 ≤2 道、同技法 ≤3 道；软约束：多轮放宽 + 兜底补足，保证凑满 size |
| R11 | 响应语义 | 客户端看到的 `match_score` 是复合分（覆盖库存初值）；`health_filter_applied` 仅"有健康档案且硬档实际剔除过"为 true；`pagination.total` 保留原始统计数（全部已发布含食材菜谱数），过滤只影响 data 条数 |

**唯一事实源**：

- 流程 / 过滤 / 评分 / 多样化：`RecipeServiceImpl::getRecommendedRecipes`（`server/services/`，权重等"可调参数"在其文件顶部常量区）
- 库存匹配 SQL / `match_score` 初值：`PgRecipeRepository::findRecommendedRecipes`（`server/repositories/`）
- 两档名单与提示文案模板：`HealthConditionLists.h`（`server/services/`；api-spec 4.2 为快照，改名单需同步 spec 修订记录）

**设计决策**：两档化见 [D-01](#d-01)；名单唯一事实源见 [D-02](#d-02)；钠阈值分级见 [D-03](#d-03)。

**边界与坑**：

- 偏好 / 健康档案读取故障：留痕（WARN）后按"无偏好 / 无档案"降级，**不把故障伪装成"未设置"**；
- 胃炎等条件不参与食材级过滤（"辛辣 / 生冷"属饮食行为，无法映射为食材黑名单），仅档案接口给建议文案；
- 多样化实为软约束，且实现与直觉有出入：首轮实际只以"同口味满 2 道"为跳过条件，技法上限在后续放宽轮才参与判定——调整该段行为前先读实现；
- 权重、加分、上限均为可调常量：改数值时按 0.4 规约同步本文档。

<a id="s2-3"></a>
### 2.3 库存语义

**职责**：管理用户库存食材的增 / 改 / 删 / 查（含 keyword 过滤），是推荐引擎的输入源。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 三维唯一 | 唯一约束 `(user_id, ingredient_name, unit)`：同名不同单位各自成行（如"料酒 15毫升"与"料酒 100克"）；同单位同名累加由服务端保证 |
| R2 | POST = 累加 | 单语句原子 UPSERT：同名同单位 → 数量累加；否则新建行。唯一约束同时充当并发闸门（替代旧"先查后写"两趟，消灭丢失更新窗口） |
| R3 | 到期日（缺省不清） | 追加带 `expiry_date` → 取行内**最早**到期日（混批安全下限，`LEAST` 忽略 NULL）；缺省 → 保留既有值 |
| R4 | PUT = 整行替换 | 编辑按 id 整行替换；**缺省 `expiry_date` = 清空该列**（替换语义，与 R3 缺省不清显式相反——否则"编辑去掉过期日期"永远无法生效） |
| R5 | 冲突收口 | 改名 / 改单位撞本人另一条 → 409「已存在同名同单位的库存条目，请直接编辑该条目」（`23505` 翻译，不由 500 兜底） |
| R6 | 字段校验 | 数量 > 0；单位 ∈ 白名单；到期日必须是真实日历日（含闰年——`2026-02-31` 在 400 拦下，不打穿 DB 变 500）。校验入口 `validateUpsertFields` |
| R7 | 过滤查询 | `findInventory` = `findInventoryFiltered` 的空词特例（SQL 单源防漂移）；keyword：trim（ASCII + 全角空格 U+3000）后纯空白 = 不过滤、UTF-8 上限 100 字节超长 400；`% _ \` 按字面匹配（ESCAPE 转义）；count 与 data 同条件保证 total 同步 |

**唯一事实源**：`PgInventoryRepository::upsertInventory` / `updateInventoryItem` / `findInventoryFiltered`（`server/repositories/`）；单位白名单 `InventoryServiceImpl::validUnits()`（api-spec 5.1 为快照；客户端 QML 有提交前拦截副本，测试强制双端同步）；keyword 收口 `InventoryHandler::trimKeyword`。

**设计决策**：三维唯一与累加 / 替换分离见 [D-04](#d-04)。

**边界与坑**：

- 勾选回流是另一条库存写入路径（触发与匹配规则见 [2.4](#s2-4)）；
- 客户端在途语义：库存页过滤词"代次化"（改词作废在途响应并立即补发）；登出 / 换号后旧会话迟到响应静默丢弃（防跨账号串台）——`InventoryViewModel::m_epoch`、回归测试 `client/tests/test_inventory_vm.cpp`。

<a id="s2-4"></a>
### 2.4 购物清单闭环

**职责**：多清单模型的购物清单管理；与推荐 / 库存构成闭环：推荐缺料 → 一键加购 → 勾选已购 → 回流库存 → 影响下次推荐。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 多清单模型 | 清单创建（可关联膳食计划 `plan_id`）/ 删除 / 详情；清单项含 需要量 / 库存量快照 / 待买量 / 单位 / 勾选态 |
| R2 | 一键加购 | 批量加入：`待买量 = max(需要量 - 库存量, 0)`，并快照当时库存量（`inventory_quantity`） |
| R3 | 勾选回流 | `checked` 假 → 真且待买量 > 0 时触发：同名同单位 → 库存累加；无同名同单位 → 按清单项单位新建行（同名不同单位旧行保留）；单语句原子 UPSERT |
| R4 | 回流仅认边沿 | 仅 `false → true` 转换触发（重复置真不重复回流）；**取消勾选不回滚库存**；取消后再次勾选会再次回流（当前语义，留意） |
| R5 | 导出仅 text | 服务端只支持 `text`（其他格式 400，参数校验在数据库操作之外）；内容为纯文本（`[x]` / `[ ]` + 去尾零数量） |
| R6 | 图片导出属客户端 | 服务端不提供；导出图片 = 客户端本地能力（`grabToImage` 截清单表格存 PNG，Qt6 返回 bool 失败兜底）——见 [D-05](#d-05) |

**唯一事实源**：`PgInventoryRepository::batchAddShoppingItems` / `updateShoppingListItem` / `exportShoppingList`；客户端图片导出 `client/qml/pages/ShoppingListDetailPage.qml`。

**设计决策**：导出契约对齐见 [D-05](#d-05)。

**边界与坑**：

- 一键加购的库存量按食材名取（不区分单位行——同名多单位时扣减基准不确定，已知简化）；
- 客户端勾选"在途合并"：快速连点只记最后一次状态、当前请求返回后自动补发，避免静默丢弃或并发覆盖（`ShoppingListViewModel::updateShoppingListItem`）。

<a id="s2-5"></a>
### 2.5 营养计算

**职责**：投稿 / 编辑时服务端按食材清单自动计算营养并入库；报告接口只读取，不实时计算。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 计算时机 | 投稿 / 编辑时由 `buildNutritionInfo` 计算，结果存 `recipes.nutrition_info`（JSONB）；报告接口不实时计算 |
| R2 | 名称规范化 | 去首尾空白 + 去中英文括号括注（"鸡胸肉（去皮）" → "鸡胸肉"）再查表 |
| R3 | 单位换算 | 质量单位直接换算；毫升 / 升按 1ml≈1g；容器单位按固定容量近似（杯≈240ml、碗≈200ml、汤匙≈15ml、勺≈10ml、茶匙≈5ml）；计数单位依赖食材表 `default_portion_g` 单重，无单重 → 无法换算 |
| R4 | 未计入不静默 | 未收录（reason=未收录）/ 无法换算（reason=无法换算）的食材进 `excluded_ingredients` 透传报告页 |
| R5 | 入库形态唯一 | 顶部四项与 `per_serving` 七项恒成对写入；`per_serving` 当前为**整道菜合计**（非单份），文案不带"单份"字样 |
| R6 | has_data 判定 | `nutritionHasData`：含 `per_serving` 且七项任一 >0 即有数据（覆盖纤维 / 钠 / 维C——纯调味料宏量全 0 但钠有值）；`findById` 与 `findNutrition` 共用，保证详情页与报告页结论一致 |
| R7 | 三级降级 | ① 未注入营养仓库 → 回退形态；② 查询异常 / 表缺失 → 有手填用回退形态、无手填返回 `nullopt`（投稿按空对象；**编辑保留库中已有营养**）；③ 全部食材不可换算 → 回退手填或空对象，附 excluded 明细。计算是增强，不阻塞投稿 / 编辑 |
| R8 | 手填语义 | 用户手填 nutrition = "可选补充"：能自动计算时以计算为准；全部不可计算时回退手填 |

**唯一事实源**：`RecipeServiceImpl::buildNutritionInfo` / `fallbackNutrition` / `gramsOf` / `normalizeIngredientName`；`PgRecipeRepository::nutritionHasData`；`PgIngredientNutritionRepository::findByNames`（批量 VALUES + LEFT JOIN LATERAL：规范名优先、支持别名、无 N+1）；种子 `server/sql/seed_ingredient_nutrition.sql`。

**设计决策**：见 [D-06](#d-06)。

**边界与坑**：

- 报告空态：`has_data:false` → 200 + 前端"暂无营养报告"（不再 400 / 全 0 假数据，v2.9）；
- `health_notes`（报告页阈值文案）与 `health_notice`（推荐卡片文案，见 2.2）是两个不同产物，勿混。

<a id="s2-6"></a>
### 2.6 认证与账户安全

**职责**：注册（两段化：邮箱验证码） / 登录 / JWT 签发与验签 / 密码修改与重置 / 注销。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | JWT | HS256、issuer=GoCook、claims userId/username/role、有效期 7 天；中间件验签 + 显式再查过期（防御性）；无 exp 视为非法 |
| R2 | 密码存储 | bcrypt（`$2a$` cost 10）+ 16 字节随机盐（OpenSSL RAND）；校验用常量时间比较（`CRYPTO_memcmp`），先比长度防越界 |
| R3 | 登录失败统一 | 用户不存在与密码错误均返回同一 401「用户名或密码错误」（防用户名枚举） |
| R4 | 注册（两段化） | 提交响应不泄露邮箱注册状态（恒 200「我们已向该邮箱发送邮件，请按邮件提示继续。」）：字段校验 400、用户名冲突 409 照常；邮箱未注册 → 验证码邮件 + 写 `pending_registrations`（15 分钟）；已注册 → 提示邮件（不建号）；`POST /api/register/verify`（邮箱 + 验证码）核验后原子建号 |
| R5 | 密码强度 | 修改 / 重置路径：≥6 位且含字母和数字（`UserServiceImpl`）；注册路径：仅 ≥6 位（api-spec 错误示例已随 v2.16 对齐） |
| R6 | 密码重置 | ① 忘记密码：用户名 + 邮箱**双匹配才发信**（不匹配 → 400「用户名或邮箱不正确」且不发信——双字段即防轰炸门槛）；6 位数字验证码（CSPRNG）；库内 15 分钟过期；SMTP 已配置 → 发邮件（失败 500）；未配置 → 令牌随响应返回（开发模式）。② 重置：令牌单次使用（同一事务内改密码 + 标记已用，防重放） |
| R7 | 注销 | 匿名化菜谱（`author_id` → NULL，内容保留）+ 删除用户行（级联清偏好 / 档案 / 库存 / 清单 / 通知 / 计划 / 收藏；评分随删） |
| R8 | 已知限制（代码注释留档） | JWT 无黑名单 / 版本号：密码修改 / 重置后旧令牌在过期前仍有效；如需立即吊销需引入 token 版本号 |

**唯一事实源**：`UserServiceImpl`（`generateToken` / `hashPassword` / `validatePassword` / `registerUser` / `verifyRegistration` / `requestPasswordReset` / `resetPassword` / `deleteAccount`）；`AuthMiddleware::authenticate`；`Validation.h`；`PgUserRepository`（`upsertPendingRegistration` / `createUserFromPendingRegistration` / `deleteAccount`）；登录 / 注册限流见 3.4。

**边界与坑**：

- 401 的三层含义：未带 token / 验签失败（中间件）；业务层统一「用户名或密码错误」；登录接口将 `ServiceException` 统一映射为 401——数据库故障也会报"用户名或密码错误"，排障先看日志（README 症状 C）；非法请求体等其余异常走 500；
- 密码重置开发模式回显令牌是刻意设计（无 SMTP 时便于调试），上线需配 SMTP；注册验证邮件在开发模式下打印到服务端日志（响应保持统一）；
- 注册路径用户名冲突仍返回 409（用户名维度枚举保持现状；本次收口目标为邮箱维度）。

<a id="s2-7"></a>
### 2.7 按需登录守卫与游客模式

**职责**：游客可浏览公开内容；需登录的读写操作在所有请求发送点统一拦截——登录后自动重放，绝不发出未授权请求。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 三档声明式标记 | 所有 API 调用在发送门面声明 `AuthMode`：`Public`（游客可调，直接发）/ `Silent`（需登录；未登录不发送、按 -2 回调失败——页面展示"登录后可用"空态）/ `Interactive`（需登录；未登录挂起 + 弹应用内登录页） |
| R2 | 单一守卫 preflight | 拦截逻辑只在 `HttpGoCookApi::sendRaw` 一处（所有 HTTP 请求的唯一出口），**保证绝不发出未授权请求** |
| R3 | 登录后重放 | `Interactive` 挂起请求入队（保序）；登录成功（tokenChanged）→ 按入队顺序补 `Authorization` 头重放；登录页被关闭 / 登出 → `cancelAuthQueue` 按 -2「请先登录」失败 |
| R4 | 统一失败文案 | -2 的文案常量 `kAuthRequiredError` 是唯一出口，VM 用它区分"守卫拦截"与网络 / 服务器错误 |
| R5 | 导航 / 动作守卫 | `Main.qml` 的 `guardedPush` / `guardAction`：需登录页面 / 操作统一走守卫弹登录页；登录页防重入（只压一层）；被拦意图登录成功后消费 |
| R6 | 会话切换防串台 | ViewModel 层防护：发起请求时记录 token 快照、回调时比对，会话已切换（登出 / 换号）的迟到响应静默丢弃（覆盖 Recipe / Inventory 两个 VM） |

**唯一事实源**：`HttpGoCookApi`（AuthMode / sendRaw preflight / replayPendingAuthRequests / -2 常量）；`client/qml/Main.qml`（guardedPush / guardAction / onAuthRequired）；迟到响应丢弃（token 快照）：`RecipeViewModel` / `InventoryViewModel`。

**设计决策**：见 [D-07](#d-07)。

**边界与坑**：守卫拦截是"预期失败"——VM 需区分 -2 与网络错误决定展示（空态 vs 网络提示）；被守卫拦下的旧登录态私有数据必须清空（见 `RecipeViewModel` 收藏处理）。

### 2.8 离线体验

**职责**：断网 / 请求失败时的读与写行为定式（v2 方向：不做写队列、不自动重放）。

**核心规则**：

| # | 规则 | 说明 |
|---|------|------|
| R1 | 写队列已拆除（定型） | 断网写操作**明确报错**、不假装成功、不后台排队：全局底部黑色 toast「网络连接失败，请检查网络」（1.5s）兜底；页面自行呈现的写操作由页面内提示负责，不重复弹全局——见 [D-08](#d-08) |
| R2 | 读分层（有缓存） | 菜谱详情：断网静默显示本地缓存（最近 20 条，`recipe_detail_cache`），零提示、与联网无异；网络恢复自动回最新 |
| R3 | 读分层（无缓存） | 内存有旧数据 → 静默显示旧数据；无数据 → 页面中心「网络连接失败」+ 重试（复用 `NetworkOfflineView` 组件 + ViewModel 的 `xxxLoadFailed` 属性，收藏页为参考模式） |
| R4 | 全局 toast 定位 | 只弹"未被页面自行呈现"的请求失败（兜底通道）；详情 / 收藏的加载类失败已在 API 层抑制（页面显示缓存或离线视图），不弹全局 |
| R5 | 网络错误分层 | 客户端区分：网络层错误（无响应）/ 业务错误（服务端 error 文案）/ 服务器问题（5xx）——决定提示方式（`errorMessageFor`） |

**唯一事实源**：`LocalDatabase`（详情缓存表、保留 20 条、启动清理 `pending_operations`）；`HttpGoCookApi::errorMessageFor`；`NetworkOfflineView` 组件与各 VM 失败属性；README §六（面向开发者的现状描述）。

**设计决策**：见 [D-08](#d-08)。

**边界与坑**：守卫拦截（-2）不算网络错误，走"请先登录"语义（见 2.7）；新页面要离线视图 = 复用组件 + VM 加失败属性。

<a id="c3"></a>
## 3. 横切机制与工程约定

<a id="s3-1"></a>
### 3.1 错误处理

- 业务层抛 `ServiceException(消息, 状态码)`；Handler 统一 `handleStandardException` 映射（唯一事实源 `ErrorHelper.h`）。
- 映射表：400 / 403 / 409 → 透传消息；404 → 「请求的资源不存在」（原始消息只进日志）；401 → 「身份验证失败」；501 → 「功能暂未实现」；未识别 → 500「服务器内部错误，请稍后重试」——**绝不把内部错误原文透给客户端**。
- 客户端侧 `errorMessageFor` 三分层（网络层 / 业务错误 / 服务器问题），见 2.8 R5。

<a id="s3-2"></a>
### 3.2 分页与响应格式

- 列表接口统一 `page`（从 1）/ `size`（默认 20，最大 100，解析时钳位）；响应统一 `data + pagination`。
- `safeTotalPages` 防除零（size ≤ 0 → 0）。
- 列表默认排序 `created_at DESC`（推荐接口例外，见 2.2）。

<a id="s3-3"></a>
### 3.3 序列化唯一出口

- 服务端所有响应 JSON 走 `JsonSerializer`；分页复用模板 `pagedToJson`（13 处分页类型各配一个 itemMapper 实例；Admin 两个分页类型因骨架域手工拼 JSON）。
- 客户端模型 → QML 走 `DataMapper`（30+ 重载）——两侧"翻译层"对称存在。

<a id="s3-4"></a>
### 3.4 限流

- 滑动窗口（每 IP + 完整请求路径的时间戳队列 + 后台清理线程，超限 429；未命中任何规则的路径按 60/分兜底）。
- 规则表（`Router::createRateLimiterRules`，按注册顺序、第一条前缀命中生效——具体规则须排在 `/api` 全局规则之前）：`/api/login` 5/分、`/api/register` 5/分、`/api/password` 3/分、`/api/admin` 30/分、`/api` 全局 60/分。

<a id="s3-5"></a>
### 3.5 数据访问样板收敛

- `executeDb` 单点（见 [D-09](#d-09)）：业务异常原样上抛、其余统一翻译、日志带调用点、`errorMsg` 必传、编译期拦截悬空返回；特例手写必须注释原因。

<a id="s3-6"></a>
### 3.6 日志与报错中文规范

- 见 [D-10](#d-10)。技术值保留英文：SQL / JSON 键 / HTTP 头 / 协议术语 / 配置键 / 日志级别前缀。

<a id="d-01"></a>
### D-01 健康忌口两档化：硬档剔除 / 软档提示 + 轻降权（2026-09）

- **背景**：健康过滤需要区分风险等级——高盐 / 高糖加工品（腊肉、咸菜等）出现即高风险，适用一票否决；盐、酱油、糖等常见调味料做菜时可少放或不放，不适用"一律排除"。
- **决策**：两档处理——硬档（任一食材命中即整道剔除）+ 软档（不剔除，附 `health_notice` 提示并轻微降权 0.03，单次）。提示措辞保守：少放 / 按需，不做绝对禁止。
- **理由**：把"强制"与"建议"分开；降权而非剔除，让"含盐的高分菜"排到清淡菜之后，而不是从列表消失。
- **被否方案**：不区分风险等级、名单命中一律排除。
- **落点**：commit `611ee65`；`RecipeServiceImpl` 过滤与评分段；`HealthConditionLists.h`；api-spec v2.10。

<a id="d-02"></a>
### D-02 忌口名单收束为唯一事实源（2026-09-05）

- **背景**：名单曾手抄于三处——推荐引擎常量、UserService 忌口建议、api-spec 4.2；任一处漂移都会造成"文案承诺 ≠ 引擎行为"。
- **决策**：`HealthConditionLists.h` 为服务端唯一名单来源；推荐引擎直接引用（硬档剔除 / 软档提示 / 文案模板）；UserService 忌口建议的食材名单由该头文件 join 生成；api-spec 4.2 定位为契约快照，改名单时同步 spec 修订记录。
- **理由**：一处定义、处处引用；"名单顺序 = 文案拼接顺序"等隐含约定固化在头文件注释里。
- **被否方案**：三处手抄 + 人工同步（随时可能漂移）。
- **落点**：commit `611ee65`；`HealthConditionLists.h` 头注释（整改 N2）。

<a id="d-03"></a>
### D-03 钠阈值按量分级接入推荐（2026-09）

- **背景**：两档名单是"食材级"判定，覆盖不了"整道钠超标但食材不在名单"的情况；营养自动计算已产出整道钠数据，具备按量判定条件。
- **决策**：高血压用户 + 整道钠 ≥800mg + 未命中软档调味料 → 附钠提示并走同一 0.03 降权；软档已命中时不重复（提示已覆盖"少盐"语义）。
- **理由**：名单与量级互补；"提示不冗余"优先于"告警最大化"。
- **被否方案**：软档命中时再叠一条钠提示（产生"含盐…；钠含量较高…"的冗余文案）。
- **落点**：commit `611ee65`；`RecipeServiceImpl::buildHealthNotice`；api-spec v2.12。

<a id="d-04"></a>
### D-04 库存单位语义重构：三维唯一 + 累加 / 替换显式分离（2026-09）

- **背景**：原二维唯一 `(user_id, ingredient_name)` 下，同名食材的不同单位互相覆盖；且添加走"先查后写"两趟，并发存在丢失更新窗口。
- **决策**：唯一约束升为 `(user_id, ingredient_name, unit)`；添加定为"同名同单位累加、不同单位新增行"，改为单语句 UPSERT（唯一约束充当并发闸门）；新增 PUT 编辑 = 按 id 整行替换（缺省到期日 = 清空，与添加缺省不清显式分离）；勾选回流按"名字 + 单位"精确匹配。
- **理由**：单位是食材语义的一部分（15 毫升料酒 ≠ 100 克料酒）；"添加是补货、编辑是纠正"——两个入口对应两种语义。
- **被否方案**：维持二维唯一（不同单位互相覆盖）；维持先查后写两趟（丢失更新窗口）。
- **落点**：commit `611ee65`；`PgInventoryRepository::upsertInventory` / `updateInventoryItem`；api-spec v2.10 / v2.11；`create_all_tables.sql`（三维唯一约束）。

<a id="d-05"></a>
### D-05 购物清单导出契约对齐现实（2026-09）

- **背景**：spec 曾声明服务端支持 `text` + `image` 两种导出，但服务端从未实现 `image`；图片导出实际由客户端本地完成。
- **决策**：契约收口为"服务端仅 `text`"（其他格式 400）；图片导出定性为客户端本地能力（`grabToImage`），spec 不再声称服务端图片导出（v2.13）。
- **理由**：契约必须等于现实——"承诺了但从未实现"的接口在联调 / 换端时爆雷成本最高。
- **被否方案**：在服务端补实现图片导出（图片渲染属客户端表现层职责，重复实现且成本高）。
- **落点**：commit `51eb175`（spec v2.13-v2.15）；`PgInventoryRepository::exportShoppingList`；`client/qml/pages/ShoppingListDetailPage.qml`。

<a id="d-06"></a>
### D-06 营养自动计算闭环（2026-08）

- **背景**：营养原靠用户手填（质量不可控、常为空）；报告页曾出现全 0 假数据。
- **决策**：投稿 / 编辑时按食材清单 + 内置营养库自动计算并入库；手填降级为"可选补充"；不可计算食材进 `excluded_ingredients` 而非静默丢弃；`has_data:false` 统一空态；三级降级保证不阻塞投稿、编辑不清空已有营养（v2.9）。
- **理由**：计算是增强不是硬依赖；数据要么真实、要么明确"暂无"，不给假数。
- **被否方案**：① 继续仅靠手填；② 无数据时返回全 0 假数据；③ 计算失败使投稿 / 编辑整体失败。
- **落点**：commit `5a1cff0`（营养库与自动计算）、`09c7c3a`（nutritionHasData 收口）；`RecipeServiceImpl::buildNutritionInfo`；api-spec v2.9。

<a id="d-07"></a>
### D-07 按需登录守卫：单一 preflight + 声明式标记（2026-08-31）

- **背景**：游客模式上线后，"需登录操作"若散落在各页面自行判断，会出现漏网（已发请求再吃 401）与交互不一致。
- **决策**：所有 API 声明 `AuthMode`（Public / Silent / Interactive）；拦截收束在发送唯一出口 `sendRaw` 的 preflight 一处；Interactive 挂起 + 登录后按序重放（补 `Authorization` 头）。
- **理由**：横切逻辑单一守卫 + 声明式标记——使用点不写 if，绝不发出未授权请求。
- **被否方案**：各调用点自行判断登录态；发送后靠 401 兜底再弹登录（请求已发出，体验与浪费都差）。
- **落点**：commit `bf78371`；`HttpGoCookApi::sendRaw` / `replayPendingAuthRequests`；`client/qml/Main.qml::guardedPush`。

<a id="d-08"></a>
### D-08 离线体验定型：写队列整体拆除（2026-08-07）

- **背景**：曾实现"断网写操作入队 + 网络恢复自动重放"（客户端待处理队列 + 服务端幂等表）。
- **决策**：整体拆除队列与幂等机制；断网写操作明确报错（全局 toast / 页面自呈现），读操作走本地缓存或离线空态；客户端启动清理遗留 `pending_operations` 表。
- **理由**：队列重放的"静默失败 / 延迟同步 / 状态漂移"体验差、复杂度高；写操作多为一键点击，恢复后手动重试成本为零（对齐主流 App 模式）。
- **被否方案**：保留队列继续打磨（曾实现过，定向放弃）。
- **落点**：commit `e04e8e3`；`LocalDatabase`（清理遗留表）；README §六。

<a id="d-09"></a>
### D-09 Repository 样板收敛：executeDb 单点（2026-08-24）

- **背景**：各 Repository 方法重复"借连接 / 开事务 / 提交 / 异常翻译"样板，异常分层与事务边界重复实现易漂移。
- **决策**：全项目唯一一处 `executeDb` 模板（`DbExecutor.h`）：常规方法只写差异部分（SQL + 参数 + 映射）；业务异常原样上抛、其余异常统一翻译且日志带调用点；`static_assert` 编译期拦截悬空返回值（引用 / 指针 / string_view / pqxx::field）；`errorMsg` 必传。
- **理由**：样板收敛减少重复；编译期拦截把"事务销毁后悬空"这类生命周期坑挡在构建阶段。
- **被否方案**：每方法手写连接 / 事务（重复且易漂移）。
- **落点**：commit `e64c318`；`DbExecutor.h`；特例保持手写并注释原因（`deleteRecipe`、`updateRecipeImage` / `updateStepImage`、`uploadAvatar` / `getHealthConditions`）。

<a id="d-10"></a>
### D-10 报错与日志中文化规范（2026-09-04）

- **背景**：历史代码中用户可见消息与日志中英文混杂。
- **决策**：服务端异常 / 日志与客户端文案全面简体中文；用户可见消息必须中文；技术值保留英文（SQL / JSON 键 / HTTP 头 / 协议术语 / 配置键）；测试断言同步。
- **理由**：面向中文用户的产品，报错信息即产品体验；日志中文便于排障。
- **被否方案**：保持英文消息（用户可读性差）。
- **落点**：commit `091b987`；全仓复扫口径保留在 `.reasonix/english-messages-audit.md`（工作底稿）。

<a id="d-11"></a>
### D-11 上传与静态服务收口：写侧规则单点 + 读侧安全兜底（2026-09-08）

- **背景**：头像 / 封面 / 步骤图三处上传各自校验（白名单 / 大小 / 类型判断拷贝三份），规则漂移风险；静态读取曾用 `httplib::set_mount_point`，无环境变量 / 安全头 / 审计。
- **决策**：写侧规则收进 `ImageUploadRules`（白名单 → 大小 → 魔数嗅探，宽容修正）；读侧自实现 `UploadFileServer`（双层防穿越 + CSP sandbox + nosniff + 日志转义）；路径映射统一 `UploadPaths`。
- **理由**：规则单点防漂移；SVG 是上传链最薄弱环节，"写侧黑名单尽力 + 读侧 CSP 兜底"双防线；自实现读侧服务可控（环境变量、安全头、审计日志）。
- **被否方案**：三处各自校验；继续用 `set_mount_point`（无定制能力）。
- **落点**：commit `658e59c`（读侧服务 + 写侧单点）、`09c7c3a`（UploadPaths 先行收口）；`server/common/ImageUploadRules.h` / `UploadFileServer.h` / `UploadPaths.h`。

<a id="d-12"></a>
### D-12 编辑保持放开：已发布菜谱可编辑（复核维持，2026-09-12）

- **背景**：2026-09 文档复核发现矛盾——1.4 错误表「仅可编辑待审核或未通过」系 2026-05-12 预注册口径（当时编辑功能尚未实现），2026-05-22 实现时选择了「放开所有状态」（4.9，实现与客户端一致），旧行未撤回；复核一度倾向收紧实现，经权衡维持放开。
- **决策**：编辑权限维持「仅限作者本人、不限状态」；编辑后恒回 `pending` 重新审核；spec 1.4 旧行按现实修正（v2.16）。
- **理由**：审核关卡天然拦截恶意毁坏（不会通过）；善意优化（修错字 / 补图 / 改用量）没有理由限制；若收紧，已发布内容既不可删也不可改，将永久冻结。
- **被否方案**：收紧为「仅待审 / 未通过可编辑」（1.4 旧行口径）——已发布内容永久冻结过于僵化；待审核流程落地后如运营需要可再评估。
- **落点**：复核结论（2026-09-12）；spec v2.16（1.4 修正）；实现与客户端维持现状（`PgRecipeRepository::update` 仅校验作者；MyRecipesPage 编辑入口全状态可见）。

<a id="d-13"></a>
### D-13 防枚举与防轰炸收口：注册两段化 + 找回双字段门槛（2026-09-12）

- **背景**：3.11.2 遗留【待决策】——SRS 曾要求差异提示「该邮箱未关联任何账户」（泄露枚举），spec 声明过"统一 200"，实现却是 400「用户名和邮箱不匹配」，三层口径打架；注册接口的 409「邮箱已被注册」同属邮箱枚举面。
- **决策**：① 注册两段化——提交恒 200 统一文案（不泄露注册状态），差异移到邮件通道（未注册发验证码邮件、已注册发提示邮件），新端点 `POST /api/register/verify` 验证码核验后原子建号；② 找回密码保留用户名 + 邮箱双字段，**双匹配即发信门槛**——不匹配 400「用户名或邮箱不正确」且不发信；成功文案「重置密码邮件已发送，请检查收件箱和垃圾邮件。」；③ 开发模式（无 SMTP）邮件内容打印服务端日志，接口响应保持统一。
- **理由**：防轰炸放在**触发条件**上（不知道完整凭据对的请求不产生邮件，优于"邮箱-only + 统一响应"可被对任意邮箱触发发信）；邮箱是否注册只体现在邮件通道（页面层不可见）；限流（/api/password 3 次/分、/api/register 5 次/分）兜底。
- **被否方案**：① SRS 的「该邮箱未关联任何账户」差异提示（直接泄露枚举）；② 仅邮箱 + 统一 200 + 差异化邮件（任意邮箱可被触发发信，轰炸面大）。
- **落点**：设计说明书体系提交（服务端 + 客户端 + 测试 + 文档；与 spec v2.17 同批落档）；`pending_registrations` 表（sql/README 含存量库迁移段）。

## 5. 数据与种子纪律

**关键约束记忆点**（全量以 `server/sql/create_all_tables.sql` 为准）：

- `inventory` 三维唯一 `(user_id, ingredient_name, unit)`（见 [D-04](#d-04)）；
- `users.username` / `users.email` 唯一；`favorites` / `ratings` 各有 `(user_id, recipe_id)` 唯一；
- 账号删除的级联策略见 2.6 R7（菜谱匿名化保留；关联数据随删）。

**种子纪律**：

- 种子数据嵌入 `INSERT VALUES`（不追加 UPDATE 语句）；脚本幂等、可重复执行；
- 营养库种子为幂等全量同步（先清空旧行再插入）——营养修正 / 扩充随重跑自动生效。

**迁移纪律**：

- 只增不删；`create_all_tables.sql` 是"清空重建"脚本，**绝不对已有数据的库手跑**（会清空全部业务数据）；
- 旧库升级用只增迁移（示例见 `server/sql/README.md`）；docker 初始化只在空数据卷执行。

<a id="c6"></a>
## 6. 设计原则清单

跨模块反复出现的设计取向（写新代码 / 评审时对照本文档）：

1. **横切收束**：横切功能必须收束为单一守卫 + 声明式标记，禁止使用点重复逻辑。实例：[D-07](#d-07) 登录守卫（`AuthMode` + `sendRaw` preflight）、[D-11](#d-11) 上传规则单点。
2. **唯一事实源**：同一规则只允许一处定义。实例：[D-02](#d-02) 忌口名单、`validUnits` 单位白名单、`nutritionHasData` 营养判定、`UploadPaths` 路径映射。
3. **契约必须等于现实**：不承诺未实现的能力；发现漂移以现实为准收口。实例：[D-05](#d-05) 导出仅 text；[D-12](#d-12) 错误表按现实修正；2026-09 两处遗留漂移已随 spec v2.16 收口（2.1 / 2.6 R5）。
4. **降级不阻塞**：辅助能力异常不阻塞主流程。实例：[D-06](#d-06) 营养计算三级降级、偏好 / 健康档案读取失败降级（2.2）。
5. **静默读、显式写**：离线时读走缓存静默展示，写明确报错不假装成功。实例：[D-08](#d-08)。
6. **单一数据库操作出口**：常规数据访问统一 `executeDb`，特例必须注释原因。实例：[D-09](#d-09)。
